## What ran

On November 20, 2026, at 20:28 UTC, Mru Flight v0.9.0 ran on ESA's OPS-SAT PRETTY satellite, the fourth and last run of experiment exp4051 of the ESA OPS-SAT Space Lab. The OPS-SAT team approved it on November 16, the package went to TU Graz the same day, and TU Graz ran it on the FlatSat on the morning of November 20.

The package, `exp4051-mru-flight-v0.9.0.tar.gz`, has the same shape as run 3: one entry script in the foreground, user space only, no network, 128 MB per process, everything written to `toGround/`. Six segments of 40 seconds run one after the other:

1. Automatic resets. Replica 1 stops answering at cycles 60 and 300. Replica 2's process is killed with SIGKILL at cycle 150, a real dead unit. The manager resets a silent replica, up to three times.
2. The same faults with resets off.
3. The same faults under fixed triple modular redundancy (TMR).
4. Three simulated sensors: a spike, a drift and a frozen sensor.
5. The same decision core as an application of NASA's core Flight System (cFS), with the faults of run 1.
6. Real bit flips in each replica process's own memory, made by software.

Segments 1 to 5 simulate each fault at its symptom, as runs 1 to 3 did: a replica's answer is changed, withheld or stopped. Segment 6 schedules no fault.

</Section>

## A unit reset, and taken back only on the right answer

When a replica is retired for silence, the F&#x2060;´ `RedundancyManager` sends a reset on its `resetOut` port and starts an admission at the next cycle. The unit comes back only if it gives the right known answer. A unit still silent gets the next reset. After `ResetLimit` resets the manager emits `ResetsExhausted` and keeps the slot retired, so a dead unit cannot cause a reset loop. A replica retired for a wrong answer is never reset.

In orbit, segment 1: replica 1 hung at cycle 60, was lost at 62, reset and taken back at 63 on its known answer. Replica 2's process was killed at 150; it was reset at 153, 155 and 157, stayed silent each time, and was kept out at 159. Replica 1 hung again at 300, was caught in self-check, reset a second time and taken back at 303. The segment ended with two units live and 394 correct results.

<Section label="Sensors">
<Fragment slot="note"><code>quorum::sensor</code> in the core, and the F&#x2060;´ component <code>SensorVoter</code> (MRU-SV-001 to 007). Five Kani proofs, 16 in the workspace. The readings are simulated.</Fragment>

## One value from readings that differ slightly

Three sensors that read the same quantity never agree to the bit, so a vote on equal values does not work for them. The core chooses one value within a tolerance: the median of three if another reading is within the tolerance of it, the midpoint of two if they agree, a single reading marked unchecked. With two readings that disagree, it delivers nothing, since nothing says which one is right. `SensorVoter` excludes a sensor only after a set number of outlier cycles in a row (5 by default), so a short spike never excludes it.

Kani proves five properties for every set of three readings and every tolerance: an agreed value is agreed and in range, an outlier is never chosen, nothing is unchecked while two or more readings are in, the median is a median, ties included, and a sensor is excluded exactly after its limit.

Segment 4 runs a spike on sensor 1 at cycle 60, a drift on sensor 2 from cycle 120, and sensor 0 frozen from cycle 260, with a tolerance of 2.00 and noise up to 0.50. In orbit, 399 cycles: 279 correct values, 0 wrong, and 120 cycles with no value after the two readings left disagreed from cycle 279. The spike was masked, and sensor 2 was excluded at cycle 137. A plain average of the same readings was wrong in 261 of the 399 cycles.

## The same core in NASA's core Flight System

The decision core also runs as a cFS application: three replicas as cFE child tasks, every decision through the core's C interface, a known-answer test of every replica before cycle 1, linked statically into one binary for the flight processor. No sample or lab application is built, so nothing opens a network socket. The app has the core's decisions and the F&#x2060;´ manager's rules around them. It does not have the automatic resets or the sensor voter; those are F&#x2060;´ only.

Segment 5 was the first run of the application on flight hardware, with the faults of run 1: a bit flip at cycle 60, a stuck replica at 120, a hung one at 240. In orbit: 400 cycles, 318 correct, 3 disagreements caught, 0 wrong, the same counts as on the FlatSat and in ESA's image. The stuck replica 1 was retired on its known answer at cycle 122, the hung replica 0 was lost at cycle 242, and replica 2 went on alone in self-check. No socket was open, and nothing was left behind. On the SEPP the process peaked at 4.5 MB of address space.

<Section label="Bit flips">
<Fragment slot="note">Requirements MRU-DEP-008 and MRU-DEP-009. Real flips, one bit at a time, made by software in user space.</Fragment>

## Closer to the cause

Segment 6 injects at the cause, not the symptom. A thread in each replica process flips one bit at a time in that process's own memory: code, read-only data, data, heap and stacks, in proportion to their size, at random times, 2 flips per second per replica. Each flip is logged before it is made. The package's files are never changed. The manager runs the shrinking quorum with a known-answer test on the last replica every cycle, and it is told nothing about the flips.

In orbit, 173 flips hit the three replicas, 149 of them in code. Replica 2 crashed after 41 flips and was lost at cycle 229. Replicas 0 and 1 delivered all 399 results to the end: 0 caught, 0 wrong, and no message dropped on the manager's links. Both then crashed at shutdown, after the last result: the flips had corrupted memory that only their exit code read. The FlatSat gave the same outcome, flip for flip, because the seed fixes when the flips come and where they land.

The flips found one real flaw before flight. On the ground, a corrupted replica sent a reply too short to decode, and F&#x2060;´'s generated port code in the manager asserted on it and ended the manager process: 1 of 64 native runs at 200 flips per second from start-up. Faults injected at the symptom never sent the manager a malformed message, so they could not find it. In 0.9.0 the manager checks every message from a replica on its link before F&#x2060;´'s hub sees it. A message that is not exactly one well-formed reply, or one more than four in a cycle, is dropped and counted. A replica that sends only garbage is then silent to the manager, and is lost. In 160 native runs after the fix, the manager never crashed.

A replica that a flip sets spinning stops at 2 seconds of CPU time, one that writes without end stops at 256 KB, and no process of the run writes a core file.

</Section>
